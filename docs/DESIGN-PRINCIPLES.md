# 数据 Agent 设计原则

> 本文是 Daw 的产品方法论，提炼自产品设计者数月真实使用的复盘（2026-08）。每条原则背后都有真实翻车案例的抽象——它们不是理想化的愿景，而是任何数据 agent 从演示走向可用时**必然撞上的问题**。文中不涉及任何具体公司的业务场景；方法论本身对所有数据 agent 普适。

## 原则一：唯一真相 —— 分析的宪法

**共同问题。** 同一个业务指标，换一张表、换一种写法，结果就不一样。多数数据助手对此的处理是来回增删条件试出一个"一致"的数字——那不是分析，是挑错。用户要的是能拿去开会的数字，对不上的数字不如没有。

**原则。** 不管用哪张表、哪种写法取数，同一个业务问题的答案必须一致。表和查询只是不同视角，不是不同真相。两路结果对不上，必然有一路逻辑有问题：必须用诊断查询把差异定位到数据（逐层对比过滤条件、按维度拆分看差异集中在哪、查重复行与空值），解释必须能被查询结果证明；定位不了就如实说"原因未定位"，绝不编造。口径先行：统计对象、时间范围、过滤条件、去重方式，先想清楚再动手；关键数字至少两条独立路径互证。

**Daw 的落地。** 数据分析场景 system prompt 的「唯一真相原则」五条（`src-tauri/src/usage.rs`）；复盘脚本的同窗对账线索（`tools/review_transcript.py`）；引擎级一致性的专项治理（如时区语义统一：会话时区显式固定，取数直接写本地墙钟字面量）。

## 原则二：语义映射是 agent 的本职

**共同问题。** 业务方只会说业务语言——"定金""业绩""有效单"。他们**无从知道**一个业务概念对应哪张表、哪个字段、什么筛选条件；如果每个概念都要人工给字段级解释，agent 才能理解得"稍微准确一些"，可用性就大打折扣。这是所有数据 agent 的生死线：语义映射（口头表达 → 业务模型 → 数据表达）做不了，选表、加条件、出数字全都无从谈起。

**原则。** 用户要的是**符合业务理解的数字，不是数据库准确的数字**。因此：

1. **先给业务理解，再给数字。** 遇到业务概念，先用一句话说出业务理解与采用的取数口径，让用户确认或纠正——说出理解后被纠正一次，远好过默默选一个口径让用户猜。确认后的映射立即沉淀，下次直接沿用。
2. **穷尽探查才可以说"没有"。** 一个公司不可能没有订单表。"数据里没有"之前先穷尽手段：表名按命名族与概念同义词多轮轮扫、候选表小成本探列、重点找 `is_*`/`type_*`/`status_*` 前缀的官方标记字段、值域分布验证。数据被拒（无权限）只说明这条路不通，不说明概念不存在。
3. **数字对但顺序错也是答错。** 口径选择本身就是交付的一部分。

**Daw 的落地。** system prompt「业务概念：语义映射是你的职责」小节；用户确认后的映射写入 OKF 知识库（concepts/tables），新会话自动继承；新概念标准接入协议沉淀为任务协议（自描述扫描 → 多源对账 → 一次人工拍板）。

## 原则三：交付纪律 —— 先答所问，数字带出处

**共同问题。** 三种典型的"正确但不可用"：问数量却输出一整套趋势看板（答非所问）；先报含水分的总量，被追问才承认大头无效（把口径噪音甩给提问的人）；结论不给来源表（用户无法信任，也无法据此申请数据权限）。

**原则。**

1. **所问即所答。** 问数量，第一句就是数字，再附口径说明；不擅自升级成趋势、看板或归因分析。叫法对不上时先说明采用的口径，不要整轮跑偏。
2. **默认报有效业务口径。** "卖了多少"的第一句就是剔除无效单、测试单、取消单后的有效成交；技术性总量只放口径脚注或对账场景。
3. **关键数字必须注明来源**——业务叫法 + 物理表名 + 统计口径。没有出处标注的数字等于不可信的数字。
4. **业务语言与物理表名两段式。** 面向业务的结论用业务语言；权限申请等技术事项必须给精确物理表名（含 schema）+ 申请理由——业务方只能拿物理表名去申请权限。

**Daw 的落地。** system prompt「交付纪律」小节；权限盲区在交付中主动附"权限申请清单"；用户个人偏好（如命名不用否定式标签）沉淀在用户画像，逐会话生效。

## 原则四：业务知识是地基，且必须持续积累

**共同问题。** 每个会话都从零理解数据：不知道表为什么存在、组织架构如何、业务机制是什么——而这些都直接决定数字的对错，不只是解释的话术。偶发的高质量交付不构成产品力。

**原则。** 表的存在都有业务理由（一张宽表往往就是一套归类规则的产品化，理解它的"为什么"才能选对它）；组织架构、业务机制（如资源分配的零和关系）决定归因的对错。因此 agent 必须：**学到的立即沉淀**（字段释义、口径、排障经验），**修正优先于并存**（新结论推翻旧结论时同步改写，禁止新旧矛盾版本并存逼着下次会话当仲裁），**知识可版本化、可回溯**。

**Daw 的落地。** 工作区 OKF 知识库：git 版本化（每次写入自动提交，提交信息带板块名与 ±行数）、写入守卫（空内容拒绝、回显标题剥离、标题归一化匹配防近似重复）、知识体检（空板块按真损失/容器/残桩分类）；用户画像随纠错持续进化（纠错记事件、观点记原则）。

## 原则五：越用越懂，且失败必须可见

**共同问题。** 两类信任崩塌：一是 agent 每单从零开始、反复犯同样的错；二是静默失败——知识"写入成功"却没落盘、自动提交其实没提交，用户发现的每一次静默失败都在透支信任。

**原则。** 沉淀 → 召回 → 按沉淀交付，三步闭环才算"越用越懂"；系统对自己的失败必须 fail-loud：凡是外部副作用（写文件、git 提交）都要检查结果，失败要进日志、要可归因；**复盘工具是产品的一部分**——用真实使用 transcript 驱动问题发现（工具时间线、慢查询、错误归因、一致性体检、知识库体检、变更审计），发现的问题配测试修复，再用真实使用验证。

**Daw 的落地。** OKF 元数据 status 生命周期（active/superseded）；`tools/review_transcript.py` 复盘脚本（「用-查-改-用」循环的固定入口）；会话回执与 git 提交信息双通道记录每次知识变更的 ±行数。
